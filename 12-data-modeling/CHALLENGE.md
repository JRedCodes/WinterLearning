# Challenge · Room Booking Schema

**Type:** 🛠️ Build · **Est:** 3–4h · **Services:** 🐘 Postgres

## Scenario

> **#team-workspace** · *Jonas (staff engineer):* We're building "Roomly", a meeting-room booking product for companies. Before anyone writes an endpoint I want the schema nailed down, because last time we let the app "handle" double bookings and support spent a quarter cleaning up. Requirements are below. The rule is simple: **if the data is invalid, Postgres must refuse it.** The tests in `test/` are our acceptance criteria. I set up a tiny migration runner. Write the migrations, and please include an ERD so product can follow along.

### The spec

All ids are generated by the database (`bigint GENERATED ALWAYS AS IDENTITY` recommended; `uuid` is accepted). All timestamps are `timestamptz`. Unless marked *nullable*, every column is `NOT NULL`.

**organizations**

| Column | Type | Rules |
|---|---|---|
| `id` | bigint / uuid | primary key |
| `name` | text | |
| `slug` | text | unique; lower-case letters and digits in words separated by single hyphens (`acme`, `acme-corp-2` ✅; `Acme`, `acme corp`, `-acme`, `acme-`, `ac--me`, `''` ❌) |
| `created_at` | timestamptz | defaults to now |

**users**

| Column | Type | Rules |
|---|---|---|
| `id` | bigint / uuid | primary key |
| `email` | text (or citext) | unique **case-insensitively** (`Dana@Example.com` and `dana@example.COM` collide); must contain an `@` that isn't the first character |
| `full_name` | text | |
| `created_at` | timestamptz | defaults to now |
| `updated_at` | timestamptz | defaults to now; **set to now on every UPDATE** (trigger) |

**memberships**: a user's membership in an organization

| Column | Type | Rules |
|---|---|---|
| `organization_id` | FK → organizations | deleting the organization deletes its memberships |
| `user_id` | FK → users | deleting the user deletes their memberships |
| `role` | text (or enum) | one of `owner`, `admin`, `member`; defaults to `member` |
| `created_at` | timestamptz | defaults to now |
| | | a user has **at most one** membership per organization |

**rooms**

| Column | Type | Rules |
|---|---|---|
| `id` | bigint / uuid | primary key |
| `organization_id` | FK → organizations | deleting the organization deletes its rooms |
| `name` | text | unique per organization **among rooms that aren't soft-deleted** |
| `capacity` | integer | greater than 0 |
| `features` | jsonb | defaults to `{}`; must be a JSON **object** |
| `created_at` | timestamptz | defaults to now |
| `deleted_at` | timestamptz, *nullable* | soft delete: NULL = live |

**bookings**

| Column | Type | Rules |
|---|---|---|
| `id` | bigint / uuid | primary key |
| `room_id` | FK → rooms | deleting the room deletes its bookings |
| `organizer_id` | FK → users | a user who organized any booking **cannot be deleted** |
| `title` | text | |
| `starts_at`, `ends_at` | timestamptz | `ends_at` strictly after `starts_at` |
| `status` | text (or enum) | `confirmed` or `cancelled`; defaults to `confirmed` |
| `created_at` | timestamptz | defaults to now |
| `updated_at` | timestamptz | defaults to now; set to now on every UPDATE |
| | | **no two confirmed bookings of the same room may overlap**. Back-to-back (10:00 end, 10:00 start) is fine; cancelled bookings never block. Must fail with SQLSTATE `23P01` (exclusion constraint). |

**booking_attendees**

| Column | Type | Rules |
|---|---|---|
| `booking_id` | FK → bookings | deleting the booking deletes its attendee rows |
| `user_id` | FK → users | deleting the user deletes their attendee rows |
| `response` | text (or enum) | `pending`, `accepted` or `declined`; defaults to `pending` |
| | | each user at most once per booking |

## Acceptance criteria

- [ ] Migration files follow `NNN_lower_snake_case.sql`, there are at least two, they apply to an empty database, and re-running applies nothing. (`test/migrations.test.ts`)
- [ ] All six tables exist with the specified columns, types and nullability; no `timestamp without time zone` anywhere. (`test/schema.test.ts`)
- [ ] Ids are generated; `created_at`/`updated_at`, `features`, `role`, `status` and `response` have the specified defaults. (`test/schema.test.ts`)
- [ ] Invalid data is rejected with the right SQLSTATE: NOT NULL `23502`, UNIQUE `23505`, CHECK `23514`, FK `23503`, exclusion `23P01` (invalid enum values may raise `22P02` instead of `23514`). (`test/constraints.test.ts`)
- [ ] Booking overlaps are rejected, including re-confirming a cancelled booking into a taken slot; back-to-back, other-room and cancelled bookings are allowed. (`test/constraints.test.ts`)
- [ ] ON DELETE behaviour: org deletion cascades to memberships, rooms, bookings and attendees but not users; organizers can't be deleted; attendee-only users can. (`test/relationships.test.ts`)
- [ ] `updated_at` moves forward on UPDATE for users and bookings. (`test/relationships.test.ts`)
- [ ] `docs/ERD.md` has a Mermaid `erDiagram` naming all six tables with relationship cardinalities. (`test/migrations.test.ts`)
- [ ] `npm test` and `npm run typecheck` pass.

## Getting started

```bash
cd 12-data-modeling/challenge
make install
make up          # Postgres 16 on localhost:5433
make test        # every test file drops the schema and re-applies YOUR migrations
```

Your inner loop:

```bash
npm run db:reset          # drop everything, apply all migrations (use this while iterating)
make psql                 # \d bookings, \d+ rooms, try inserts by hand
npm run test:watch
```

Because tests rebuild from scratch, you can freely edit your migrations while you work. (The runner refuses edited migrations on a database where they were already applied: that's what `db:reset` is for.)

## Rules

- Don't modify `test/` or `src/`.
- Plain SQL in migrations. No ORM, no schema generator.
- Enforce rules with **constraints** (and the one trigger for `updated_at`). Don't implement uniqueness or overlap checks with triggers.
- Name your constraints (`CONSTRAINT rooms_capacity_positive CHECK …`). Module 13 maps those names to API errors.

## Stretch goals

1. Add an index on every foreign key column that isn't already the left-most column of an index. Check with `\d` which ones you missed.
2. Write a `004_room_floor.sql` migration that adds a required `floor integer` column to `rooms` **as if the table had millions of rows**: nullable first, backfill, then `NOT NULL`. Write the steps as comments if a real backfill doesn't make sense here.
3. Enforce "the organizer must be a member of the room's organization" in the schema. (Hint: denormalize `organization_id` into `bookings` and use composite foreign keys, or reason about why you'd rather leave it to the service layer.)
4. Add an `audit_log` table and a trigger that records every change to `bookings.status` (who/what/when; use `current_setting('app.user_id', true)` for "who").
5. Allow bookings to be at most 8 hours long and to start on a 5-minute boundary, with `CHECK` constraints.
